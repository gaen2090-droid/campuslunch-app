# 기획안: 매장별 혼잡도 예측을 앱에 노출하기

상태: **기획 단계 (미구현)** · 작성: 2026-10-15
배경: 어드민 "혼잡도 AI 예측" 탭에서 모으고 있는 매장별·시간대별 예측을 앱 이용자에게도 보여주고 싶다.

> 이 문서는 대화로 정리한 기획을 그대로 옮긴 것이다. 구현 전에 "6. 결정 사항"을 먼저 확정한다.

---

## 1. 요구사항 (원문 정리)

1. 시간대별 "자리 있을 확률" 예측 데이터가 **있는 매장만** 노출한다.
2. 구간 안에 최신 제보가 있는 매장은 제보가 우선이고, **구간 안에 제보가 없으면 예측을 보여준다.**
3. 어디까지나 **데이터 기반 확률이며 최신 제보가 아니라는 점**을 명시한다.
4. 새 제보가 쌓일수록 확률이 시시각각 변한다. 예측이 없던 매장도 데이터가 쌓여 예측이 생기면 **바로** 노출된다.
5. 확률이 실시간으로 변한다는 것을 이용자도 알 수 있게 한다.
6. 지도에도 반영한다.

## 2. 현재 상태 (코드 기준 사실)

### 2.1 예측 데이터 (어드민)
- RPC `admin_crowd_prediction_lunch()` (`supabase/crowd_prediction.sql`): **평일 12:00~13:02(KST), 15분 4구간**(720/735/750/765분). 구간 끝은 2분 겹침.
- 대상: `restaurants.crowd_enabled = true`. 제외: 통계 제외 유저(관리자 제보 전용 계정 예외), `영업안함` 제보, 주말.
- 같은 유저·매장·구간·날짜는 최신 1건만 반영. **구간 표본 3건 미만이면 `데이터 부족`**(`predicted_level = null`).
- **확률 계산 (확정)**: 서버 함수 `crowd_relax_probability()` (`supabase/crowd_prediction_relax_probability.sql`).
  ```
  여유로울 확률(%) = round( (입장가능 + 0.5×약간혼잡 + 1) ÷ (전체 + 2) × 100 )
  ```
  - 입장가능(=앱 표기 `바로입장`) 1.0 · 약간혼잡 0.5 · 자리없음 0, 라플라스 보정(+1/+2).
  - 약간혼잡 가중치는 0.5로 유지하기로 함(0.7 검토 후 보류. 0.7이면 약간혼잡만 쌓인 매장이 67%로 초록 문턱 70%에 붙음).
  - 어드민 색 구간: 70% 이상 초록 · 40~69% 주황 · 40% 미만 빨강.
- 어드민 호출은 `admin_crowd_prediction_lunch_v2()` (원본을 감싸 `relax_probability` 추가).

### 2.2 앱 홈 (`lib/screens/home_screen.dart`)
순서: `바로 입장 가능해요` → `빈자리 조금 있어요` → **`혼잡도를 알려주세요`** → `붐비고 있어요` → `영업 종료` 버튼.
- `혼잡도를 알려주세요`: 검정 점 + `제보필요` 배지, `NeedsReportCard` 최대 5개, 더보기는 목록 화면의 `stamp` 모드.
- `NeedsReportCard`: 이미지 · 이름 · `지역 · 종류` · 우측 `제보하면 스탬프 2개` 칩. 혼잡도 표시 없음.
- 상태 섹션은 30분 이내 제보 우선, 없으면 오래된 제보를 `30분 이상 지난 제보예요.`로 표시.
- **`제보필요`(= `hasCrowdUpdate == false`) 기준은 "이번 영업 세션 시작 이후 제보 0건"** (`supabase_restaurant_repository.dart` `_mergeRow`). 시간(30분) 기준이 아니다.

### 2.3 앱 지도 (`lib/widgets/restaurant_kakao_map.dart`, `lib/screens/map_screen.dart`)
- 실제 지도는 **카카오맵 마커**. `_FakeMap`은 대체용.
- 마커: `바로입장` 초록 · `약간혼잡` 앰버(`FFBF00`, 지도 전용 색) · `자리없음` 빨강 · **`제보필요` = 검정 원 + 흰 별**(`StarPinPainter`, 스타일 `pin_no_report`) · `영업안함`/제보 비대상 = 회색 핀.
- 범례(`_CrowdLegend`)는 3색. 별 마커는 `스탬프 지급 기준` 배지/시트에서 설명.
- 필터 칩: `제보있음` / `제보없음` 등.
- 선택 카드: 제보필요 매장은 `스탬프 2개 받기`, 그 외 `혼잡도 제보하기`.

### 2.4 갱신 구조
- **실시간 구독/폴링 없음.** 앱 복귀·제보 후 등에 `refreshRestaurants()`로 다시 받는다. 홈의 1분 타이머는 스탬프 시간대 화면 갱신용.
- → "실시간"이라는 표현은 과장. 새로 가벼운 폴링이 필요하다.

### 2.5 알려진 제약
- 예측은 **평일 12:00~13:02 · 구간 표본 3건 이상 · crowd_enabled 매장**에서만 존재한다. 그 밖의 시간대에는 예측 UI가 나타나지 않는 것이 정상.
- 운영 DB에서 `표본 3건 이상인 매장×구간` 수를 먼저 조회해 실제 노출 규모를 확인할 것(미조회).

## 3. 설계 결정 (잠정)

### 3.1 예측을 보여줄 대상
**`hasCrowdUpdate == false`(세션 제보 0건) 매장만.**
- 이미 `혼잡도를 알려주세요`에 있는 집합이라 새 기준이 필요 없다.
- 세션에 오래된 제보가 있으면 기존대로 상태 섹션의 `30분 이상 지난 제보예요`로 노출. 한 매장이 상태 섹션과 예측에 동시에 걸리는 충돌을 피한다.

### 3.2 홈
- **상태 섹션 4개는 그대로 둔다**(확인된 제보만). 새 섹션을 만들지 않는다(섹션 과다로 묻히는 문제).
- **`혼잡도를 알려주세요` 섹션 안에서만 예측을 보여준다.** 이 섹션은 제보를 유도하는 자리(`제보하면 스탬프 2개`)라서, 예측 매장을 빼면 제보 유도가 사라져 데이터가 안 쌓이는 악순환이 생긴다.
  ```
  혼잡도를 알려주세요   [점심 예측 포함 ⓘ]        제보필요
  ┌ 매장명                                   [제보하면 스탬프 2개]
  │ 지역 · 종류
  │ 점심 예측  여유로울 확률 82%  ·  최근 9건 기준     ← 예측 있을 때만
  ```
- 정렬: 예측 있는 매장을 **확률 높은 순**으로 위에, 그 아래는 기존 정렬(가까운순/인기순). 지금 5개만 보이므로 상위 5개가 의미를 가진다. 더보기 목록(`stamp` 모드)도 동일.
- `제보하면 스탬프 2개` 칩은 유지(제보 유도).
- 제보가 들어오면 다음 갱신 때 이 섹션에서 상태 섹션으로 올라간다.
- **추천 배너, 점메추 요정, 룰렛에는 예측을 쓰지 않는다**(확인된 제보만 추천).

### 3.3 지도
- 검정 별은 "제보하면 스탬프"의 상징이므로 **유지**하고, 예측 있는 제보필요 매장은 **별 원 바깥 링에 예측 색**(초록/주황/빨강)을 둔다. 예측이 없으면 지금과 같은 별.
- 범례에 `★ 링 색 = 예측` 한 줄, `스탬프 지급 기준` 시트에도 한 줄 추가.
- 선택 카드: 상태 자리에 `여유로울 확률 82% · 예측`, 버튼은 기존 `스탬프 2개 받기` 유지.
- 필터 `제보없음`에는 예측 있는 매장도 그대로 포함.
- **시간 구간 칩(12:00/12:15/12:30/12:45)은 1차에서 제외**(필터줄이 이미 복잡). 다른 구간 미리보기는 2차.
- 구현 시 카카오 마커 스타일(링 3종) 등록 필요. 작은 핀에서 링 색이 구분되는지 **시안을 먼저** 확인할 것.

### 3.4 데이터·갱신
- **신규 RPC `app_crowd_prediction()`**: 일반 사용자(authenticated)용. 매장·구간별 확률·표본 수·건수만 내려주고 개인 식별 정보는 없다. 계산은 서버 `crowd_relax_probability()`를 그대로 사용(앱/어드민 기준 일원화).
- 예측을 저장하지 않고 **조회 시점에 계산** → 오늘 들어온 제보가 표본에 즉시 반영되고, 표본이 3건을 넘기면 다음 갱신 때 자동 노출.
- 앱 갱신: 예측 RPC만 **평일 11:50~13:05, 홈/지도가 보일 때 90초 간격 폴링**(잠정).
- `Restaurant` 모델은 건드리지 않고, Provider가 `restaurantId → 현재 구간 확률` 맵을 들고 있는다.

### 3.5 이용자에게 보이는 문구
- 태그: `데이터 기반 예측`, `최근 평일 점심 N건 기준`
- 갱신: `제보가 쌓이면 바로 바뀌어요 · n분 전 갱신` ("실시간" 단어는 쓰지 않는다)
- 확률 변화 시 `▲ 5%p` 같은 표시를 잠깐 노출(선택)
- ⓘ 안내 시트: "과거 점심 제보를 모아 계산한 값이에요. 새 제보가 오면 바로 달라져요. 실제와 다를 수 있어요."

## 4. 검토했다가 접은 안

| 안 | 접은 이유 |
|---|---|
| 새 `예측` 섹션을 따로 추가 | 홈 섹션이 이미 5개라 묻힘 |
| 예측 매장을 상태 섹션(바로입장/약간혼잡/자리없음)에 섞기 | "확인된 곳"의 신뢰가 흐려짐. 상태 섹션 카드에는 제보 유도 CTA도 없음 |
| 예측 매장을 `제보필요`에서 빼기 | 제보 유도가 사라져 예측 데이터가 더 안 쌓임 |
| 약간혼잡 가중치 0.7 | 약간혼잡만 쌓인 매장이 67%로 초록 문턱(70%)에 붙고, 바로입장과의 구분력이 줄어듦. 순위 영향은 거의 없음 |
| `제보필요` → `데이터부족`으로 개명 | 행동을 시키는 말이 사라지고(상태 설명이 됨), 예측이 생긴 매장에는 의미가 어긋남. 예측 기능 도입 시점에 다시 판단 |

## 5. 작업 단계

1. DB: `app_crowd_prediction()` RPC (+ 운영 DB 표본 현황 조회)
2. 앱: Provider 로드/폴링, 홈 `NeedsReportCard` 예측 줄·정렬·안내 시트
3. 앱: 지도 링 마커 스타일, 범례, 선택 카드 (시안 먼저)
4. 지표: 예측 노출/클릭 이벤트를 `feature_event`에 추가(어드민 지표 연동)
5. 2차: 지도 시간 구간 칩, 점심 외 시간대 확장

## 6. 결정 사항 (이어서 할 때 가장 먼저 확정)

- [ ] **예측 대상**: 세션 제보 0건 매장만(권장) vs 현재 15분 구간 기준으로 넓히기(오래된 제보 매장도 예측 노출 → 상태 섹션과 중복 위험)
- [ ] **지도 링 마커 시안**: 별 + 색 링이 작은 핀에서 구분되는지 확인
- [ ] **폴링 간격**: 90초(잠정)
- [ ] **블록 문구**: `점심 예측 포함` / `이 시간엔 보통 이래요` 등 이름
- [ ] **최소 표본**: 앱 노출용을 3건 그대로 둘지, 5건으로 올릴지
- [ ] 운영 DB 표본 현황 조회(노출 규모 확인)
